## 1. Цель задачи и фильтр `ponytail` (6-Step Decision Ladder)

**Цель:** в коробке `L1DDER` появляется скилл `/l1-fast` на RU и EN. Он раскладывается во все агенты как слэш-команда, назван в сводке `AGENTS.md` / `CLAUDE.md` исключением из `Roadmap Gate` и правила двух остановок и проверяется `doctor`. Это `US-1`–`US-4` и часть `US-6` из [`requirements.md`](../../../../specs/FEAT-006-fast-mode/requirements.md).

**Каркас скилла** (шаги и их критерий завершения):

| Шаг | Что делает агент | Готово, когда |
|-----|------------------|---------------|
| «Для чего эта команда» | Простым языком: небольшая фича продукта, ты описываешь, агент уточняет и после «ок» сам делает и проверяет всё, документы после кода | — |
| 1. Роадмап | Читает `docs/roadmap.md`. Позиция `1 (CURRENT)` занята → строгий отказ без правок файлов: закончи спринт через `/l1-task` или отклони его с откатом через `/l1-planning`. Баг → `/l1-hotfix`, правка самого проекта → `/l1-chore` | `CURRENT` пуста, задача — фича продукта |
| 2. Уточнение и масштаб | Короткие раунды `grilling`, 4 признака масштабной работы; сработал признак → предупреждение и обычный путь, решает пользователь | Развилки закрыты, масштаб оценён |
| 3. Решение + `⛔ СТОП №1` | Карточка: что делаем, решение (`ponytail`, `codebase-design`), швы и тесты, файлы, 1–3 задачи, ID к брони (`IDEA`, `FEAT`, `SPRINT`, `TASK`) | «ок» получен |
| 4. Бронь в роадмапе | До кода: строка `1 (CURRENT)` с ID, `🚧 реализация`, `режим: /l1-fast` + запись в историю | Строка записана |
| 5. Реализация | `tdd` по срезам, скиллы стека; вырос объём → остановка и новая оценка | Код и тесты готовы |
| 6. Полная самопроверка + `⛔ СТОП №2` | `make ci`, `ponytail-review`, `code-review` (Standards + Spec), `ponytail-audit`, `ponytail-debt`, `make test-e2e` и живой прогон, `diagnosing-bugs` на каждый баг, Docs Sync, `retro`; находки чинит и прогоняет весь список заново; результаты + сценарий ручной проверки + футер `ponytail` | «ок» человека после ручной проверки; замечание → назад к шагу 5 и весь список заново |
| 7. Реестры | `ideas.md`, `backlog.md`, спека из 3 файлов, README спринта, `plan.md` (записан после реализации) и `summary.md` задач и `TASK-NN.99`; строка `Режим \| /l1-fast` в паспортах; `make ci` + `doctor`; коммит; спринт в «Завершённые» | Все реестры заполнены, коммит сделан |
| Exit Gate | Чек-лист | Все пункты отмечены |

**Фильтр `ponytail`:**
- **Что переиспользуем:**
  - структуру и тон `l1-chore/SKILL.md`: раздел «Для чего», граница, карточка, `Exit Gate`;

- **От чего отказываемся:**
  - кода в CLI для `/l1-fast`: агент работает по тексту скилла;
  - новых шаблонов и полей в шаблонах (решение `Q4`);
  - отклонения спринта: это `TASK-05.02`;
  - правок правил, словаря и шаблона роадмапа: это `TASK-05.03`.

- в правиле двух остановок: «в `/l1-fast` обе остановки в чате, `plan.md` пишется после кода».

В `TASK-05.03` сводку останется только сверить.

## 5. Риски и открытые вопросы

- Шаг 1 скилла отсылает к отклонению спринта в `/l1-planning`, которого до `TASK-05.02` нет. Это временное расхождение внутри `dev`, релиз до конца спринта не выпускается.
- До `TASK-05.03` правила говорят только о двух исключениях, а сводка в `CLAUDE.md` уже назовёт `/l1-fast`.
- Пока идёт работа, `IDEA-NNN` и `FEAT-NNN` забронированы только в строке роадмапа. Параллельный `/l1-idea` их не видит и может взять тот же номер. Для этого шаг 3 скилла велит считать следующий номер с учётом строк роадмапа, а шаг 7 — перепроверить номера перед записью и при совпадении взять следующий свободный.
- Скилл длинный: 7 шагов и список проверок. Если он выйдет заметно длиннее `/l1-task`, вынесу список проверок шага 6 в ссылку на `doctor-checklist-template.md` по правилу `writing-for-agents`, без изменения смысла.
