## 1. Цель задачи и фильтр `ponytail` (6-Step Decision Ladder)

**Цель:** у каждой новой версии `L1DDER` есть чёткая инструкция агенту, сборка без неё падает, а `npx l1dder update` после каждого обновления печатает блок «🤖 Инструкция для ИИ-агента», который агент обязан выполнить. Так старые проекты получают правки своих защищённых файлов (например, строку `/l1-chore` в `40-skills-router.mdc`) без потери своих настроек (`US-6`).

**Фильтр `ponytail`:**
- **Что переиспользуем:** `getPendingReleases()` и `compareSemver()` из `src/changelog.ts` (порядок пропущенных версий уже готов); подставляемый каталог `deps.releasesCatalog` / `deps.targetVersion` в `runCli` (так уже тестируется `BREAKING CHANGES`); проверку верхней записи в `scripts/sync-release-meta.mjs` (там уже падает сборка без `version`); стиль блока «🤖 Инструкция для ИИ-агента» из `src/cli.ts`.
- **От чего отказываемся:** слияние маршрутизатора в коде и маркеры в файлах (решение пользователя); вывод `agent` в `CHANGELOG.md` и заметки к релизу (поле только для агента); проверку старых записей `releases.json` (обязательно с версии новее `1.1.0`); флаг, чтобы отключить блок.
- **Публичные швы для тестирования (`Seam 4` из `design.md`):**
  - `runCli(["update", ...], { targetVersion, releasesCatalog })` — `tests/cli.test.ts`: блок 🤖 и его содержимое в выводе;
  - `scripts/sync-release-meta.mjs` как процесс — `tests/sync-release-meta.test.ts`: код выхода и сообщение;
  - `buildEntryPointSummary()` — `tests/cli.test.ts`: правило «после `update` выполни блок 🤖».

## 3. Критерии готовности (DoD)

**Агент проверяет:**

| # | Критерий | Точная команда / способ проверки |
|---|----------|----------------------------------|
| 1 | `update` всегда печатает блок 🤖 при смене версии (шаги, пустой список, старые версии, порядок, `--skills`), без смены версии — нет | `npx vitest run tests/cli.test.ts` |
| 2 | Сборка падает без `agent` у новой версии и при расхождении RU и EN | `npx vitest run tests/sync-release-meta.test.ts` |
| 3 | Сводка `AGENTS.md` / `CLAUDE.md` требует выполнить блок 🤖 | `npx vitest run tests/cli.test.ts` |
| 4 | Текущий `assets/releases.json` (верхняя `1.1.0`) собирается без изменений | `make build` |
| 5 | Полный цикл без ошибок | `make ci` |

**Пользователь проверяет (при желании):**

- Как выглядит блок 🤖 в выводе `update` (покажу в отчёте).

## 4. Артефакты и границы Scope

**Трогаем:**
- `src/changelog.ts` — поле `agent` в `ReleaseEntry`, `formatAgentUpdateSteps()`.
- `src/cli.ts` — вывод блока после `update` / `sync`.
- `src/agents.ts` — одна строка в разделе об обновлении сводки (RU и EN).
- `scripts/sync-release-meta.mjs` — проверка `agent` у верхней версии новее `1.1.0`.
- `tests/cli.test.ts`, `tests/sync-release-meta.test.ts`.
- `AGENTS.md` (правило 3, выше блока), `l1dder/rules/30-tech-stack.mdc` (раздел 4).
- Сгенерированное сборкой: блок `l1dder:begin` в `CLAUDE.md` / `AGENTS.md`.

**НЕ трогаем (вне Scope):**
- `assets/releases.json`: новую версию и её `agent` записываем только при выпуске; текст шагов для ближайшего релиза уже лежит в `design.md`.
- `CHANGELOG.md`, `scripts/render-release-notes.mjs`, `scripts/release.mjs`.
- `40-skills-router.mdc` в `assets/` и слияние файлов при `update`.
- Документация для пользователей о блоке 🤖 — одной строкой в Living Docs Sync на `TASK-04.99`.

## 5. Риски и открытые вопросы

- Порог «новее `1.1.0`» зашит в скрипт сборки одной константой. Это осознанный срез: `// shortcut: обязательность agent с версии после 1.1.0, убрать порог, если когда-нибудь заполним agent у старых версий`.
- Блок печатается и при `--yes` / `--force`; агент, который сам запускает `update`, видит его в том же выводе.
