# Банк Идей — L1DDER

> **Методология:** L1DDER (100% Dogfooding)
> **Скилл управления:** `/l1-idea` (создание идей) + автоматическое обновление статусов из `/l1-feature` и `/l1-task`.
> **Формат ID идеи:** `IDEA-NNN` (три цифры с ведущими нулями: `IDEA-001`, `IDEA-002`...).
> **Последнее обновление:** 2026-11-04

---

## Справочник статусов и приоритетов (использовать символ-в-символ)

**Статусы `IDEA-NNN`:**
- `📋 нереализована` — идея записана в банк, ждёт проработки в фичу (`/l1-feature`).
- `🚧 реализация` — по идее создана фича (`FEAT-NNN`) в `docs/backlog.md` и/или идут спринты.
- `✅ реализована` — все связанные с этой идеей фичи (`FEAT-NNN`) перешли в статус `✅ реализована`.
- `❌ отклонена` — идея отклонена (причина записана в карточке).

**Приоритеты:**
- `P0` — Критично / Ядро MVP
- `P1` — Высокий приоритет
- `P2` — Средний приоритет
- `P3` — Низкий приоритет / На будущее

### IDEA-001: Базовое ядро L1DDER v1.0.0 (Zero Hidden State, Multi-Agent CLI, skills.json, RU/EN, Docs Site) {#idea-001}

#### Суть идеи и ценность
Объединить методологию `L1 METHOD` (Zero Hidden State, 6 слэш-команд `/l1-*`, сквозные паспорта `ID Passport`, `Doctor Checklist`) с тонким мульти-агентным CLI `l1dder` (`init`, `update`, `sync`, `skills`, `changelog`, `doctor`), манифестом `l1dder/skills.json` (20 скиллов в коробке), полной поддержкой `ru`/`en` и двуязычным сайтом документации на GitHub Pages.

### IDEA-002: Предрелизный гигиенический спринт: автотест на 2 моделях (Composer и Grok) в playground, аудит ponytail и релиз v1.0.0 {#idea-002}

| Поле паспорта | Значение |
|---------------|----------|
| **ID идеи** | `IDEA-002` |
| **Приоритет** | `P0` |
| **Статус** | `✅ реализована` |
| **Связанные фичи (`FEAT-NNN`)** | [`FEAT-002`](./backlog.md#feat-002) |
| **Дата создания** | 2026-10-21 |

#### Суть идеи и ценность
Перед публичной выкаткой `l1dder@1.0.0` провести полноценный гигиенический спринт по собственным правилам догфудинга: подготовить изолированный полигон `playground/`, прогнать полностью автоматический E2E-тест наших скиллов и правил на **2 разных быстрых моделях (`Composer` и `Grok`)**, провести ревизию всего кода и текстов через `ponytail` и все 20 скиллов с устранением любых шероховатостей, и выполнить выкатку `v1.0.0`.

#### Ключевые сценарии / Как это работает
1. **Полигон `playground/` и тест на 2 моделях (`Composer` и `Grok`):**
   - Скрипт `playground/prepare.mjs` создаёт изолированные песочницы (`playground/sandboxes/composer` и `playground/sandboxes/grok`), инициализирует в них `l1dder` и размещает стартовый мини-проект.
   - Две разные модели (`Composer` и `Grok`) независимо проходят цепочку скиллов `L1DDER` (`/l1-idea` → `/l1-feature` → `/l1-planning` → `/l1-task` с `ID Passport`).
   - Автоматический верификатор `playground/verify.mjs` жёстко проверяет созданные обеими моделями артефакты (наличие файлов, точность всех сквозных ID `IDEA-001`, `FEAT-001`, `SPRINT-01`, `TASK-01.01`, `TASK-01.99`, таблицы паспортов и статусы).
2. **Аудит через `ponytail` и все скиллы (`ponytail-audit`, `ponytail-review`, `ponytail-debt`, `code-review`, `codebase-design`):**
   - Проверка кода `src/` и текстов `assets/i18n/{ru,en}/` на оверинжиниринг, дублирование, несоответствие ссылок и исправление найденных косяков.
3. **Выкатка релиза `v1.0.0`:**
   - Финальная проверка `make ci`, `npm pack --dry-run`, подготовка git-репозитория и публикация `v1.0.0` на GitHub и npmjs.

#### Итоги брейншторма и ограничения (`ponytail` / YAGNI)
- **Что входит в базовый объём:** `playground/{prepare,verify}.mjs`, реальный прогон на моделях `Composer` и `Grok`, полный аудит `ponytail` + фикс замечаний, подготовка и выкатка `v1.0.0`.
- **Что откладываем / не делаем:** облачные платные бенчмарки со сторонними API-ключами — используем доступные локально субагенты `Composer` и `Grok`.

### IDEA-003: SEO-база сайта и витрин проекта (sitemap, метаданные, превью, `llms.txt`, GitHub, npm, README) {#idea-003}

| Поле паспорта | Значение |
|---------------|----------|
| **ID идеи** | `IDEA-003` |
| **Приоритет** | `P1` |
| **Статус** | `✅ реализована` |
| **Связанные фичи (`FEAT-NNN`)** | [`FEAT-003`](./backlog.md#feat-003) |
| **Дата создания** | 2026-11-01 |

#### Суть идеи и ценность
Сделать так, чтобы поисковики и ИИ-ассистенты правильно понимали L1DDER, а по названию находилась актуальная информация. Это необходимая база, но не источник популярности: она нужна до внешних упоминаний, которые будут вести на сайт.

#### Ключевые сценарии / Как это работает
- Поисковик получает `sitemap.xml`, а у каждой страницы есть свои заголовок, описание, канонический адрес и связь с версией на другом языке.
- Ссылка на сайт показывает аккуратное превью с картинкой, а ИИ-ассистенты читают карту сайта в `llms.txt`.
- На GitHub и в npm актуальное описание и темы, а в README указано произношение названия.
- Перед релизом строгий гейт доказывает, что сайт работает не хуже, чем до правок.

#### Итоги брейншторма и ограничения (`ponytail` / YAGNI)
- **Что входит в базовый объём:** техническая база сайта, `llms.txt`, витрины GitHub, npm и README, подключение Google Search Console и Яндекс Вебмастера, строгий гейт сайта и релиз `v1.0.3` по отдельному подтверждению.
- **Что откладываем / не делаем:** новые статьи и страницы, Хабр и другие внешние упоминания, свой домен, JSON-LD.

### IDEA-004: Команда `/l1-chore` для служебных правок вне роадмапа {#idea-004}

| Поле паспорта | Значение |
|---------------|----------|
| **ID идеи** | `IDEA-004` |
| **Приоритет** | `P2` |
| **Статус** | `📋 нереализована` |
| **Связанные фичи (`FEAT-NNN`)** | — |
| **Дата создания** | 2026-11-04 |

#### Суть идеи и ценность
В любом проекте есть работы, которые не меняют поведение продукта для его пользователей: CI, зависимости, настройка окружения, правила для агентов. Сейчас им нет места в процессе: `/l1-task` требует спринта в роадмапе, а `/l1-hotfix` рассчитан на баги, поэтому такие правки делаются без следа в трекере. Команда даёт им короткий путь со своим журналом и не ослабляет роадмап-гейт для фич.

#### Ключевые сценарии / Как это работает
- Пользователь вызывает `/l1-chore обнови CI`, агент предлагает варианты с рекомендацией и после подтверждения делает правку, прогоняет проверки и записывает `CHORE-NNN` в `docs/backlog.md`.
- Если правка меняет поведение продукта, команда останавливается и предлагает `/l1-task` или `/l1-hotfix`.
- В уже работающем проекте, где в бэклоге нет журнала служебных правок, команда сама добавляет этот раздел: `npx l1dder update` файлы в `docs/` не перезаписывает.

#### Новые термины доменного словаря (`domain-modeling`)
- **Служебная правка (`CHORE-NNN`)** — изменение внутренней кухни проекта, не меняющее поведение продукта для его пользователей; выполняется вне роадмапа и записывается в журнал в `docs/backlog.md`.

#### Итоги брейншторма и ограничения (`ponytail` / YAGNI)
- **Решения:** одна остановка после обсуждения вариантов (как в `/l1-hotfix`), приоритет `P2`: полезно всем, но никого не блокирует.
- **Что входит в базовый объём:**
  - скилл `/l1-chore` на RU и EN;
  - раздел журнала в шаблоне бэклога и формат `CHORE-NNN` в общем стандарте ID;
  - термин в словаре и обновление счётчиков команд и скиллов в документации и тестах.
- **Что откладываем / не делаем:**
  - автоматическое определение границы «продукт или нет»: граница описывается правилом и решается вместе с человеком;
  - спеки, спринты и `plan.md` для служебных правок.
- **Для будущей спеки:**
  - это изменение продукта, нужен релиз;
  - команд станет 8 и скиллов 21, цифры указаны в `README.md`, путеводителе, главной странице сайта и `tests/cli.test.ts`;
  - раздел 6 в `l1dder/rules/30-tech-stack.mdc` заменяется ссылкой на новую команду;
  - ломающих изменений не ожидается.

### IDEA-005: Режим `/l1-fast`: небольшая фича сначала в коде, документы по ходу работы {#idea-005}

| Поле паспорта | Значение |
|---------------|----------|
| **ID идеи** | `IDEA-005` |
| **Приоритет** | `P2` |
| **Статус** | `📋 нереализована` |
| **Связанные фичи (`FEAT-NNN`)** | — |
| **Дата создания** | 2026-11-04 |

#### Суть идеи и ценность
Для небольшой фичи полный путь через идею, спеку, планирование и `plan.md` занимает больше времени, чем сам код. `/l1-fast` позволяет быстро обсудить задачу и сразу реализовать её, а все реестры заполнить по ходу работы или в конце. Меняется только порядок: документация идёт вторым планом, а контроль качества остаётся полностью.

#### Ключевые сценарии / Как это работает
- Пользователь вызывает `/l1-fast добавь экспорт в CSV`, агент оценивает масштаб и, если фича небольшая, предлагает решение. После «ок» он пишет код по `ponytail` и `tdd`, проходит самопроверку и ждёт приёмки, затем заполняет реестры.
- Если срабатывает признак масштабной работы, агент предупреждает и предлагает обычный путь через `/l1-idea` и `/l1-feature`. Решение остаётся за пользователем.
- Если объём вырос в процессе, агент останавливается и оценивает заново.

#### Новые термины доменного словаря (`domain-modeling`)
- **Быстрый режим (`/l1-fast`)** — путь для небольшой фичи, где документы заполняются по ходу работы или после кода, с теми же ID и проверками и с пометкой `режим: /l1-fast`.

#### Решения по итогам обсуждения
- **Честная документация:** реестры заполняются полностью, те же ID и файлы, но с пометкой `режим: /l1-fast` и настоящими датами. Документы не выдают себя за написанные заранее.
- **Две остановки в чате, без `plan.md` заранее:** первая после обсуждения («ок» на то, что делаем), вторая после самопроверки и ручной проверки, до записи документов и коммита. Экономия идёт на документах, а не на контроле.
- **Признаки масштабной работы (достаточно одного):**
  - больше 3 задач или не хватит одного спринта;
  - новая модель данных, внешняя интеграция или архитектурное решение, требующее ADR;
  - ломающие изменения;
  - нужен отдельный разбор требований, за одно обсуждение не уложиться.
- **Если признак сработал:** агент предупреждает и предлагает обычный путь, решение за пользователем. Если пользователь настоял, это записывается в итог. Если объём вырос в процессе, агент останавливается и оценивает заново.
- **Роадмап:** `/l1-fast` работает только при пустой позиции `1 (CURRENT)`. Иначе он предлагает закончить спринт или сменить очередь через `/l1-planning`, параллельной работы нет.

#### Итоги брейншторма и ограничения (`ponytail` / YAGNI)
- **Что входит в базовый объём:**
  - скилл `/l1-fast` на RU и EN: оценка масштаба по признакам, две остановки в чате, заполнение всех реестров в конце;
  - полная цепочка документов: `IDEA-NNN`, `FEAT-NNN` с короткой спекой, `SPRINT-NN`, `TASK-NN.MM`, `TASK-NN.99`;
  - неизменные требования: `ponytail`, тесты по срезам, `make ci`, ревью, E2E, ручная приёмка и `Doctor Checklist`;
  - работа не считается завершённой и не коммитится финально, пока реестры не заполнены;
  - исключение в роадмап-гейте и в правилах про две остановки, только при пустой позиции `CURRENT`.
- **Что откладываем / не делаем:**
  - послабления в тестах и проверках, в том числе «по желанию»;
  - автоматическую оценку масштаба по коду или диффу: хватит проверяемых признаков;
  - релиз внутри режима: он, как и везде, только по отдельной просьбе.
- **Для будущей спеки:**
  - связь с `/l1-chore` ([`IDEA-004`](#idea-004)): `/l1-chore` для служебных правок без изменения поведения продукта, `/l1-fast` для небольших фич продукта;
  - формулировка «единственное исключение — `/l1-hotfix`» есть в `20-workflow.mdc`, словаре, путеводителе, шаблоне роадмапа, скилле хотфикса и `src/agents.ts`, на двух языках;
  - ещё одна команда и скилл в счётчиках документации и в `tests/cli.test.ts`;
  - ломающих изменений не ожидается.
