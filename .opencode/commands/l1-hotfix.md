# L1DDER — Цепочка 5: Экстренный хотфикс (`/l1-hotfix`)

> **ПРАВИЛО ДЛЯ МОДЕЛИ:** Выполняй инструкцию строго по шагам 1 → 2 → 3 → 4 → 5. Это единственное исключение из `Roadmap Gate` для срочных багов.
> **ЖЕЛЕЗНЫЙ ГЕЙТ ОТЛАДКИ (`diagnosing-bugs`):** Тебе **запрещено** угадывать причину и менять код приложения до тех пор, пока ты не воспроизвёл баг падающей командой/тестом (`RED Gate`) или явной ошибкой в окружении. Не меняй рабочий код до получения слова «ок» от пользователя на Шаге 2.

---

## Справочник форматов (копируй символ-в-символ)

- **Формат ID хотфикса:** `HOTFIX-NNN` (три цифры: `HOTFIX-001`, `HOTFIX-002`...).
- **Связанный ID:** указывается `FEAT-NNN` / `TASK-NN.MM` (если баг относится к конкретной фиче/задаче) либо `—` (если баг общесистемный).
- **Статус после выполнения:** `✅ реализована`

---

## ШАГ 1: Прочитай `docs/backlog.md`, вычисли `HOTFIX-NNN` и пройди `RED Reproduction Gate` (`diagnosing-bugs`)

1. Прочитай `docs/backlog.md` (Раздел `3. Журнал Хотфиксов (HOTFIX-NNN)`).
2. Найди наибольший номер `HOTFIX-NNN` и прибавь `+1` (если записей нет — `HOTFIX-001`).
3. Определи, к какой фиче `FEAT-NNN` или задаче `TASK-NN.MM` относится баг.
4. **Пройди `RED Reproduction Gate` (`diagnosing-bugs`):**
   - Прежде чем строить теории, найди или напиши минимальный тест / команду, который **прямо сейчас падает (`RED`) на этом баге**.
   - Проверь все места вызова проблемной функции через `Grep` и `Read` (`ponytail`).

---

## ШАГ 2: Покажи краткий план хотфикса в чате и ОСТАНОВИСЬ (`⛔ СТОП`)

Выведи пользователю в чат карточку хотфикса:

```markdown
### План экстренного хотфикса `HOTFIX-NNN`

| Поле | Значение |
|------|----------|
| **ID хотфикса** | `HOTFIX-NNN` |
| **Связанный ID** | `FEAT-NNN` / `TASK-NN.MM` (или `—`) |
| **Воспроизведение (`RED Gate` — `diagnosing-bugs`)** | `[точная команда / тест / шаг, который сейчас падает]` |
| **Причина бага** | [Где и почему возникает ошибка — 1–2 предложения] |
| **Минимальный фикс (`ponytail`)** | [Какие конкретно файлы и строки меняем] |
| **Проверка (`GREEN Gate`)** | Падающий тест переходит в `GREEN` + `make ci` |
```

⛔ **СТОП:** Спроси: *«Вносим хотфикс `HOTFIX-NNN` (ок / правки)?»* и жди ответа.

---

## ШАГ 3: Исправь код и убедись, что `RED` стал `GREEN` (ТОЛЬКО после слова «ок»)

1. Если падающий регрессионный тест ещё не был записан в тестовый файл — запиши его и убедись, что он падает (`RED`).
2. Внеси минимальное исправление в код (без попутного рефакторинга других файлов — `ponytail`).
3. Запусти команду воспроизведения и убедись, что она стала зелёной (`GREEN`).
4. Запусти полный цикл `make ci` (`lint` + `typecheck` + `test` + `build`).

---

## ШАГ 4: Запиши `HOTFIX-NNN` в `docs/backlog.md` (и обнови доку при необходимости)

1. Открой `docs/backlog.md` и добавь строку в таблицу `## 3. Журнал Хотфиксов (HOTFIX-NNN)` строго по образцу:

```markdown
| `HOTFIX-001` | `FEAT-001` / `TASK-01.01` | 2026-10-21 | Сброс фильтра при пустом query | Проверка пустой строки в parseQueryFilter | ✅ реализована | `fix(search): preserve tag filter on empty query` |
```

2. Если хотфикс изменил поведение, описанное в `docs/concept/` или `docs/specs/FEAT-NNN-<slug>/` — сразу обнови соответствующий раздел документации.

---

## ШАГ 5: Чек-лист самопроверки перед ответом (Exit Gate)

Проверь все 4 пункта:
- [ ] 1. Команда/тест воспроизведения прошла путь `RED → GREEN`, и `make ci` завершился с 0 ошибок?
- [ ] 2. Регрессионный тест сохранён в репозитории?
- [ ] 3. Строка `HOTFIX-NNN` со связанным ID (`FEAT-NNN` / `TASK-NN.MM` или `—`) и статусом `✅ реализована` записана в Таблицу 3 файла `docs/backlog.md`?
- [ ] 4. Документация в `docs/concept/` или `docs/specs/` обновлена (если менялось контрактное поведение)?
